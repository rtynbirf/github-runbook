# ТОКЕН-КОНВЕРТ 2026-11-09 · github-runbook · П-74 (#98)

Статус: контур готов (конверт-документ + реестр + часовой + воркфлоу). Сама ротация
и отзыв ключей — решение и действие Хозяина: волна токенами не располагает и в сеть не ходит.
Принцип: ноль вечных ключей. Каждый долгоживущий секрет имеет владельца и дату смерти.

## 1. Три канала доступа (целевая схема)

| Канал | Чем ходим | Что храним | Срок жизни |
|---|---|---|---|
| Воркфлоу роя | встроенный `GITHUB_TOKEN` job + OIDC (`permissions`/`id-token` по job) где возможно | секретов не храним | время job |
| Единственный человеческий ключ | fine-grained PAT, скоуп-минимум | ровно один активный ключ | ≤ 90 дней |
| Межагентные действия | GitHub MCP Server v2: first-party идентичность + аудит-трейл | личных PAT нет | на время работы агента |

Контекст: два классических PAT уже светились в переписке — их ротация и отзыв
обязательны (решение Хозяина); этот конверт задаёт контур, в который они ложатся.

## 2. Чек-лист перехода (что кому заменить)

- [ ] Оба классических PAT из переписки пометить «отзыв после волны ×5».
- [ ] Составить перечень интеграций под этими PAT: у кого какой скоуп реально нужен.
- [ ] Выпустить один fine-grained PAT: срок ≤ 90 дней, скоупы = минимум из перечня.
- [ ] Перевести интеграции на новый ключ по одной, проверяя зелёность прогонов.
- [ ] Воркфлоу, ходившие под PAT, перевести на `GITHUB_TOKEN`/OIDC.
- [ ] Внести выживший ключ в `token-registry.json` (label, kind, scopes, expires_at).
- [ ] Отозвать оба классических PAT после подтверждения зелёных прогонов.
- [ ] Отметить факт отзыва в issue #98; реестр без записей `classic` — целевое состояние.

## 3. Правила fine-grained

1. Срок: не больше 90 дней; дата истечения обязательна и попадает в `expires_at`.
2. Скоупы: только те репозитории и права, без которых интеграция не работает;
   никаких «repo на всё сразу» и прав «про запас».
3. Ротация: новый ключ → запись в реестре (`rotated_at`) → перевод интеграций → отзыв старого.
4. Отзыв после волны ×5: временные ключи волны живут не дольше календаря §4;
   продление — только явным решением Хозяина с пометкой в issue #98.

## 5. Приёмки машинные (что проверяет сканер/часовой)

- `token-registry.json` читается `json.loads`; верхний уровень — объект с `entries`
  (массив) либо сам массив.
- Каждая запись: `label` — непустая строка; `kind` ∈ classic / fine-grained / app;
  `scopes` — массив; `expires_at` = `YYYY-MM-DD` или null; `rotated_at` =
  `YYYY-MM-DD` или null; `note` — строка. Нарушение схемы → exit 2.
- Запись с `kind: classic` = 🔴 (классика запрещена целевой схемой) → exit 1.
- `expires_at: null` у записи non-app = 🟡.
- Дней до истечения ≤ 7 (или ключ уже истёк) → 🔴, exit 1; ≤ 30 → 🟡; иначе 🟢.
- Скрипт-часовой: `tools/token_expiry_watch.py`; `--selftest` печатает `SELFTEST OK` без сети.
- Воркфлоу: `.github/workflows/token-expiry-watch.yml`, дом `wave5-token-watch`,
  пн 07:00 UTC + `workflow_dispatch`, checkout пином `actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4`.
